## 一、 长肥管道（LFN）与带宽时延积（BDP）物理建模

在长距离跨国通信中，网络链路上同时在物理光缆中“正在飞行传输”的数据量上限，由 **带宽时延积（Bandwidth-Delay Product, BDP）** 决定：

$$
\text{BDP} = C \times \text{RTT}_{\min}
$$

* $C$：链路瓶颈带宽（Bottleneck Bandwidth, bps）；
* $\text{RTT}_{\min}$：链路物理传播往返时延（秒）。

### 1.1 典型跨境算例

假设用户拥有一条 $1000\text{ Mbps}$ 宽带，访问美国洛杉矶服务器，物理 RTT 为 $160\text{ ms}$（0.16 秒）：

$$
\text{BDP} = 1000 \times 10^6 \text{ bps} \times 0.16 \text{ s} = 160,000,000 \text{ Bits} = 20 \text{ MB}
$$

这意味着：**在任何一个时间切片内，整条跨太平洋海底光缆中必须同时容纳 20 兆字节（约 13,700 个以太网数据包）的在途数据流（In-Flight Packets），才能让千兆带宽完全处于饱和打满状态！**

如果发送端的拥塞窗口因算法误判骤降至几百 KB，千兆光纤将处于严重的空载闲置状态。

## 二、 CUBIC 算法的致命死穴：丢包即腰斩的加法与三次曲线缺陷

Linux 内核长期默认的 **CUBIC** 算法是基于三次函数方程设计的“丢包驱动型（Loss-based）”协议：

$$
W_{\text{cubic}}(t) = C(t - K)^3 + W_{\max}
$$

### 2.1 为什么 CUBIC 适应不了现代跨境网络？

```
拥塞窗口 (CWND)
   ▲
Wmax ──┐               ┌───┐               ┌───┐
     │  \             /     \             /     \
     │   \ 腰斩 (乘法减小)    \ 腰斩        /     \
     │    \ 50%       /       \           /       \
Wmax/2─── └───► 漫长爬升 ─────── └───► 漫长爬升 ─────── └───►
     ──────────────────────────────────────────────────► 时间 (t)
               (在 160ms RTT 下每次爬升需要数十秒)
```

1. **盲目将非拥塞丢包判定为网络过载**：CUBIC 诞生的时代，网络链路多为高质量局域网或短途内网，丢包通常意味着交换机缓冲区打满溢出。但在跨境长途传输中，数据包跨越十几个 AS 自治域，光纤微弯损耗、无线跳频、运营商 QoS 抖动都会产生**随机非拥塞丢包**；
2. **重回峰值周期极度漫长**：一旦窗口减半，在 $160\text{ ms}$ 高延迟下，每一次窗口微调都需要经过漫长的单次往返（Round-Trip）。往往还没等窗口恢复到能跑满带宽的水平，下一个微小的随机丢包又接踵而至，导致吞吐量永久被死死压制在几 Mbps 的极低水平。

## 三、 Google BBR 核心状态机原理解析：BtlBw 与 RTprop 双参数驱动

为了打破以丢包为信号的落后范式，Google 团队提出了 **BBR（Bottleneck Bandwidth and RTT）** 架构。

BBR 坚信：**真正的拥塞发生在交换机队列开始排队膨胀的那一刻，而不是随机丢包的那一刻。**

```
吞吐量 / 延迟
   ▲
   │                     【BBR 最佳工作点 (Kleinrock Point)】
   │                                   │
   │      (未充分利用带宽)             ▼ (最佳充填)     (进入排队与缓冲区膨胀)
带宽 ├───────────────────────────────┐
   │                               │ \
   │                               │  \ 拥塞丢包区
   │                               │   \
延迟 ├───────────────────────────────┘    \────────────────►
   │
   └──────────────────────────────────────────────────────► 在途数据量 (In-Flight)
                                   ▲
                                  BDP
```

### 3.1 BBR 的四大内部状态机

1. **Startup（启动阶段）**：以指数级（2/ln2 增益）快速探顶瓶颈带宽；
2. **Drain（排空阶段）**：一旦探测到瓶颈，立即降低发送速率，排空之前建立的队列积压；
3. **ProbeBW（周期带宽探测）**：绝大部分稳态时间处于该阶段，以 8 周期循环微调发送速率，动态适应上游物理带宽变化；
4. **ProbeRTT（时延探测）**：每隔 10 秒将发送窗口压低至 4 个数据包持续 200ms，以获得链路最真实的物理底线延迟 $\text{RTprop}$。

## 四、 BBRv1、BBRv2 与 BBRv3 的演进与公平性博弈

| 协议版本 | 核心发布节点 | 核心机制升级 | 缺陷与争议 | 最适应用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **BBRv1** | 2016 (Linux 4.9+) | 首创 BtlBw/RTprop 模型，激进发包抢占 | 对 CUBIC 流量极不友好；在浅队列交换机容易引发排队自损 | 恶劣跨境单边直连加速 |
| **BBRv2** | 2019 (Alpha/Beta) | 引入显式拥塞通知（ECN）与丢包容忍阈值（2%） | 状态机较为复杂，吞吐量相比 v1 稍有保守 | 混合流多租户云 IDC 环境 |
| **BBRv3** | 2023+ (Google 内部重构) | 优化了探测退避算法，修复突发丢包降速过激，全面兼容 Linux 6.x | 需较新的 Linux 内核版本支持 | 现代高端 Linux 服务器与前沿网关 |

## 六、 Linux 生产级内核参数一键优化实操落地

在 Linux 代理网关、软路由或 VPS 节点上，执行以下优化可使 BBR 发挥最大效能：

```bash
# 1. 编辑内核网络参数配置文件
sudo tee /etc/sysctl.d/99-tcp-bbr.conf << 'EOF'
# 启用 Fair Queue (FQ) 队列调度 (BBR 强依赖 FQ 实施精准定速发包)
net.core.default_qdisc = fq

# 设置默认 TCP 拥塞控制为 BBR
net.ipv4.tcp_congestion_control = bbr

# 扩大 TCP 读写缓冲区以匹配跨境长肥管道 BDP
net.core.rmem_max = 67108864
net.core.wmem_max = 67108864
net.ipv4.tcp_rmem = 4096 87380 33554432
net.ipv4.tcp_wmem = 4096 65536 33554432

# 开启 TCP 窗口缩放 (RFC 1323)
net.ipv4.tcp_window_scaling = 1

# 禁用慢启动重启 (避免空闲后重新探速)
net.ipv4.tcp_slow_start_after_idle = 0
EOF

# 2. 立即加载使配置生效
sudo sysctl --system

# 3. 验证 BBR 是否成功运行
sysctl net.ipv4.tcp_congestion_control
lsmod | grep bbr
```

## 七、 AEO 结构化高频 FAQ 知识库

### Q1: 在专线（IEPL / IPLC）网络下，还需要折腾 BBR 吗？
> **答**：在真正的企业级物理专线（如晚高峰丢包 $< 0.05\%$）环境下，CUBIC 和 BBR 的表现差距微乎其微，因为专线几乎不产生非拥塞随机丢包，CUBIC 可以稳定维持最大窗口。BBR 最大的威力在于**公网直连（CN2 / 9929 / 普通 163）以及长距离跨洋、恶劣 WiFi 弱网环境**。

### Q2: 为什么开启了 BBR 之后，看视频依然偶尔卡顿？
> **答**：BBR 优化的是**传输层的速率自适应能力**。如果丢包发生在本地局域网（如劣质 Wi-Fi 路由器信道干扰）、或者服务器端总上行物理带宽已经被完全超售挤占至 100%，BBR 也无法无中生有。必须结合底层的 [晚高峰运营商互联质量](/benchmark/telecom-unicom-cmcc-peak-loss) 进行联合排障。
