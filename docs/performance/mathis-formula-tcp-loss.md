## 一、 Mathis 经典公式的几何与代数推导

1997 年，计算机科学家 Matthew Mathis 等人在 SIGCOMM 论文中提出了著名的稳态 TCP 吞吐量模型：

$$\text{Throughput} \le \frac{\text{MSS}}{\text{RTT} \cdot \sqrt{p}} \times C$$

其中：
- $\text{MSS}$（Maximum Segment Size）：最大报文段长度，以太网默认通常为 $1460 \text{ 字节} = 11,680 \text{ bits}$；
- $\text{RTT}$（Round-Trip Time）：往返时延（单位：秒）；
- $p$：网络丢包率（Packet Loss Rate，$0 < p \le 1$）；
- $C$：拥塞避免常数，对于标准 AIMD（加法递增乘法减小）TCP，推导值为 $C = \sqrt{\frac{3}{2}} \approx 1.22$。

```
拥塞窗口 CWND
    ▲
Wmax│           /|          /|          /|   <-- 遭遇丢包，窗口减半！
    │          / |         / |         / |
    │         /  |        /  |        /  |
    │        /   |       /   |       /   |
Wmin│_______/____|______/____|______/____|____
    0       t1          t2          t3       时间 (RTT周期)
           [--- 周期 T ---]
```

### 严谨推导过程：
1. **周期间隔内的发包总数**：
   设丢包率为 $p$，意味着平均每发送 $1/p$ 个数据包就会遭遇一次丢包，触发一次窗口减半：
   $$\text{Packets per Cycle} = \frac{1}{p}$$
2. **梯形几何面积积分**：
   在图示的一个锯齿波周期内，窗口从 $W_{\text{min}} = \frac{1}{2} W_{\text{max}}$ 线性增加到 $W_{\text{max}}$，持续时间为周期的 RTT 轮数。
   梯形面积即为发送的总包数：
   $$\text{Area} = \frac{W_{\text{min}} + W_{\text{max}}}{2} \times (\text{Duration in RTTs}) = \frac{3}{8} W_{\text{max}}^2$$
3. **联立代数方程解出最大窗口**：
   $$\frac{3}{8} W_{\text{max}}^2 = \frac{1}{p} \implies W_{\text{max}} = \sqrt{\frac{8}{3p}}$$
   每个 RTT 发送的平均包数为 $\bar{W} = \frac{3}{4} W_{\text{max}} = \sqrt{\frac{3}{2p}} \approx \frac{1.22}{\sqrt{p}}$。
4. **最终吞吐量公式落地**：
   每秒发送的数据量（比特率）等于平均每轮包数乘以 MSS 除以 RTT：
   $$\text{Throughput} = \frac{\bar{W} \times \text{MSS}}{\text{RTT}} = \frac{1.22 \times \text{MSS}}{\text{RTT} \times \sqrt{p}}$$
   **数学结论：吞吐量被死死限制在与 $\sqrt{p}$ 成反比的上限内，与本地物理接入带宽毫无关系！**

## 二、 中美跨洋链路吞吐断崖算例

假设用户使用中国电信宽带访问美西机房服务器，物理往返时延 $\text{RTT} = 160\text{ ms} = 0.16\text{ s}$，$\text{MSS} = 1460\text{ 字节}$：

| 网络承载与晚高峰丢包率 | 丢包率 $p$ | 理论单流吞吐上限 (Mathis 公式) | 相当于百兆/千兆利用率 | 真实应用体验 |
|---|---|---|---|---|
| **企业级 IEPL 专线** | **0.01% (0.0001)** | **89.06 Mbps** | 轻松跑满 4K 60FPS 杜比视界 | 毫秒级秒开，随拖随放 |
| 优质 CN2 GIA 精品公网 | 0.20% (0.0020) | **19.91 Mbps** | 可观看 1080P/4K 平稳 | 偶有 1~2 秒首帧缓冲 |
| 晚高峰普通公网中转 | 1.00% (0.0100) | **8.91 Mbps** | 严重萎缩至不足 10M | 视频强制降画质至 720P |
| 晚高峰 163 骨干拥塞 | **3.00% (0.0300)** | **5.14 Mbps** | 千兆宽带只剩 0.5% | 频繁卡顿转圈缓冲 |
| 恶劣免费节点 / 烂线路 | **10.00% (0.1000)** | **2.82 Mbps (约 350KB/s)** | 彻底沦为拨号小水管 | 网页打不开，连接超时 |

> [!CAUTION] 核心残酷现实
> 哪怕你的本地光纤有 2000Mbps，只要跨洋链路有区区 **1% 的丢包**，TCP 拥塞控制就会将你的单流速度压制在 **8.9 Mbps** 以内！这就是为什么晚高峰公网无法流畅看 4K 的根本力学原理。

## 三、 为什么 Speedtest 测速无法测出此现象？

很多人会反问：“我晚高峰跑 Speedtest 明明显示有 600Mbps，为什么开 YouTube 还是卡？”

```
[Speedtest 多连接下载模式]
线程 1 (遭遇丢包减速) ───\
线程 2 (正在高速发包) ────┼───> 多线程流量叠加: 显示 600 Mbps (产生虚假繁荣)
线程 3 (遭遇丢包减速) ───/

[YouTube / 网页真实单流加载]
单一 TCP / QUIC 数据流 ───────> 遭遇丢包 -> 窗口骤降 -> 实际吞吐跌至 5 Mbps -> 视频卡死！
```

现代 Web 浏览器基于 HTTP/2 或 HTTP/3 规范，一个页面或一条视频切片通常只建立 **单条 TCP / UDP 会话**。当这条会话遭遇丢包时，无法利用并发掩盖缺陷，直接承受 Mathis 惩罚。

## 四、 BBR 算法能完全免疫 Mathis 公式吗？

Google BBR（Bottleneck Bandwidth and RTT）算法不再依据“是否丢包”来减小窗口，而是通过探测链路的**最大投递速率与最小物理 RTT**来控制发包，因此在面对 $1\% \sim 5\%$ 的随机丢包时，BBR 确实能保持极高的发包速度。

**但是，BBR 无法违背物理极限**：
1. **真实丢包依然会导致丢包重传**：丢失的数据包依然需要接收端发出 SACK 并等待服务端重传，这会引发严重的**队头阻塞（Head-of-Line Blocking）**；
2. **严重丢包时的 ACK 丢失**：如果丢包率超过 $15\%$，连反向的 ACK 确认包都会大面积丢失，BBR 内部的状态机会误判网络崩溃而被迫进入降速探针阶段。
3. **根本解法**：唯一的终极方案只有从物理层消灭丢包——即采用晚高峰丢包率严格保持在 **0.05% 以下的真企业专线（IEPL/IPLC）**。

## 五、 Iperf3 自动化单流压测审计实录

不要使用多线程 Speedtest 掩耳盗铃，在终端中执行严格的单流长周期压测：

```bash
# -c 指定服务端 IP, -p 端口, -t 压测 60 秒, -P 1 强制单线程, -R 服务端向客户端下行测速
iperf3 -c <专线海外落地IP> -p 5201 -t 60 -P 1 -R
```

### 结果对比：
- **真专线输出**：整个 60 秒过程中，每个 1 秒间隔的吞吐量保持在一条平滑横线上（如 `95.2 Mbits/sec, Retr: 0`）；
- **公网中转输出**：出现剧烈锯齿波动，伴随大量重传（如 `Retr: 142`），速率在 3Mbps 到 30Mbps 之间剧烈震荡。
